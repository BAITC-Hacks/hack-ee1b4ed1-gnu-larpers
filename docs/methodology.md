# Методика baseline

## Вход и область применимости

Контракт входа соответствует предоставленному стартеру: `nodes(gid, depth, is_seed)`, `edges(src, dst, sum_kzt, n_tx, depth)`, `transactions(src, dst, date, sum_kzt)`. Глубина узлов 0–4, рёбер 1–4; seed соответствует нулевой глубине. Даты имеют дневную точность. Данные могут содержать изоляты и повторяющиеся транзакции.

Проверяются обязательные столбцы, пропуски, целочисленные ID, уникальность узлов и направленных пар рёбер, наличие всех концов рёбер в nodes, положительные суммы, даты, суммы и количества транзакций по каждой паре. Деньги переводятся в целые тиыны с допуском 0,000001 ₸ для шума float; положительное значение не может округлиться в ноль. Дубли транзакций не удаляются. Нет предположения, что все исходные клиенты обязательно имеют переводы.

Валидация не подтверждает происхождение данных и полноту банковской истории. По описанию выборки отсутствуют переводы за другие месяцы, другие банки и ниже порога. Входящие связи seed-клиентов неполны. На четвёртом колене исходящий обход завершён.

## Признаки графа

Все клиенты добавляются в направленный граф до рёбер. Самопереводы сохраняются в исходных таблицах, общих оборотах и отдельных `self_tx`/`self_minor`, но исключаются из степеней, признаков ролей, центральностей и дневного сопоставления. Они не создают внешнего контрагента.

| Признак | Определение |
|---|---|
| `in_deg`, `out_deg` | Число разных внешних отправителей и получателей |
| `in_tx`, `out_tx` | Количество наблюдаемых внешних транзакций |
| `in_minor`, `out_minor` | Суммы внешних входящих и исходящих в тиынах |
| `pagerank` | Направленный PageRank с весом по сумме, alpha=0.85 |
| `betweenness` | Нормированное посредничество по направленным кратчайшим путям, без весов |
| `seed_sources` | Число других seed, из которых достижим узел по направлению рёбер |
| `neighbor_clusters` | Число разных групп среди непосредственных соседей обоих направлений, включая собственную группу, если в ней есть сосед |
| `cycle_component_size` | Размер сильной компоненты с циклом; 0 без цикла; 1 при самопереводе |
| `reciprocal_neighbors` | Число внешних соседей со связями в обе стороны |
| `pass_through` | `out_minor/in_minor`; неопределён при нулевом входе |
| `truncated_by_depth` | `depth==4` и нет внешних исходящих |

Сумма ребра не используется как расстояние: большой денежный поток не должен становиться автоматически длинным путём. PageRank и посредничество описывают разные свойства. Достижимость seed не доказывает, что его деньги прошли по всем этим путям. Цикл в месячном графе может не иметь хронологически возможного обхода.

## Временные признаки

Сначала внешние переводы агрегируются по клиенту и дате. Для каждого дня исходящие объёмы сопоставляются с ещё не использованными входящими предыдущих 1–3 дней (окно настраивается). Старые поступления исключаются; оставшиеся расходуются FIFO. Входящие текущего дня добавляются после обработки исходящих, поэтому порядок событий внутри одного дня не выдумывается. Каждый тиын входящего объёма используется не больше одного раза.

`following_days_matched_minor` — объём, совместимый с таким сопоставлением; `following_days_out_share` — его доля от всех наблюдаемых входящих. Это условная совместимость сумм и дат, а не атрибуция средств. Неизвестные остатки на счетах и внешние поступления не восстанавливаются.

`same_day_activity_days` считает даты с активностью в обе стороны; `active_days` — дни внешних переводов. `max_daily_out_share` показывает концентрацию исходящих в одном дне. Если последний входящий слишком близок к последней наблюдаемой дате для полного окна, ставится `temporal_right_censored`; недостаток последующих данных нельзя считать доказательством задержки денег.

## Группы

Louvain запускается на явно ненаправленной проекции: обе стороны каждой пары суммируются, вес равен `log1p(sum_kzt/5000)`. Логарифм уменьшает доминирование единичных крупных переводов. Это осознанная эвристика группировки; направленные роли и исходные денежные суммы сохраняются отдельно. Самопереводы исключены из проекции, изолят получает собственную группу.

Вход сортируется, random seed фиксирован, группы нумеруются по минимальному gid. Результат воспроизводим при фиксированных версиях зависимостей и параметрах. Это не гарантирует устойчивость к изменению данных или resolution. Две группы при разных resolution не следует автоматически считать одной и той же организацией.

Гипотеза группы описывает сбор, распределение или передачу средств по составу ролей. Нельзя установить торговлю, зарплатный проект, конкретный бизнес или незаконную деятельность только из этих полей.

## Роли и приоритет

Для положительных значений признака считаются внутривыборочные процентильные ранги с усреднением связок; нули получают 0. Это относительное сравнение в текущей выгрузке, не универсальные банковские пороги.

Каждой роли назначается поддержка. Выбирается максимальная; при равенстве действует фиксированный порядок. Одна основная роль упрощает выгрузку, но не исключает смешанного поведения.

| Роль | Условия и поддержка |
|---|---|
| consolidator | Не меньше 3 отправителей. 0,40 × min(in_deg/8,1) + 0,30 × in_deg/(in_deg+out_deg) + 0,15 × процентиль входящей суммы + 0,15 × процентиль входящего количества |
| distributor | Симметричное правило по исходящим |
| transit | Есть обе стороны, клиент не seed, отношение меньшей суммы к большей ≥0,5. 0,45 × баланс + 0,35 × временная доля + 0,20 × min(active_days/5,1) |
| terminal | Есть входящие, нет исходящих. 0,55 + 0,15 × процентиль входящей суммы |
| coordinator | Есть обе стороны, процентиль посредничества ≥0,85, минимум 2 соседние группы и 2 достижимых источника seed. 0,40 × процентиль посредничества + 0,20 × min(neighbor_clusters/3,1) + 0,20 × min(seed_sources/5,1) + 0,20 × min((in_deg+out_deg)/10,1) |
| peripheral | Базовая поддержка 0,30; при отсутствии внешних связей — 0 и недостаточность наблюдений |

После выбора terminal на границе получает не больше 0,20 и статус `boundary_hypothesis`. Это обязательная роль из словаря стартера для наблюдаемого конечного узла, а не доказанный конечный получатель. Terminal-seed получает не больше 0,35. При правом временном обрезании поддержка transit умножается на 0,85. Эти поправки — явные эвристики, не откалиброванные вероятности.

Приоритет = 0,25 × процентиль посредничества + 0,20 × процентиль суммарного оборота + 0,15 × процентиль числа переводов + 0,15 × min(seed_sources/5,1) + 0,15 × поддержка роли + 0,10 × временная доля. Для seed последнее слагаемое равно нулю; для узлов без внешних связей весь приоритет равен нулю. Сортировка — по убыванию приоритета, затем по gid. Большой балл означает полезность исследования в рамках этой формулы.

PageRank, циклы и суточная концентрация экспортируются как дополнительные наблюдения, но не добавляются скрыто в балл. Коэффициенты и пороги пока не подобраны по экспертной разметке. Качество проверяется на поведении, инвариантах и конкретных примерах; accuracy/precision/recall без разметки не заявляются.

## Что ещё проверять с экспертами

Нужны экспертная проверка ведущих узлов и смешанных ролей, чувствительность групп к параметрам и сравнение приоритета с простой сортировкой по обороту. `role_score` описывает эвристическую поддержку, а не откалиброванную вероятность. Конкурсные CSV содержат только фиксированные поля ТЗ; дополнительные признаки и неопределимые значения сохраняются в JSON. Для доказательства направления конкретных денег потребуются дополнительные сведения о транзакциях, времени и остатках; текущий baseline этого не утверждает.

## Альтернативные роли и проверяемые ответы

В дополнение к основной роли экспортируются применимые кандидаты с исходными оценками до поправок за границу глубины, неполноту входящих seed и конец временного окна. Разница двух лучших кандидатов показывает близость гипотез, но не статистическую уверенность. При отсутствии наблюдаемых внешних переводов список пуст, разница недоступна. Приоритет раскрывается через точные вклады существующей формулы.

Конец временного наблюдения определяется по исходным транзакциям, включая самопереводы. Самопереводы по-прежнему не участвуют в сопоставлении внешних входящих и исходящих объёмов.

AI не рассчитывает новые показатели. Проверяемые утверждения содержат ссылку на основание, разрешённое поле и точное значение; сервер сверяет их с данными текущего анализа и формирует текст факта. Произвольное резюме и гипотезы остаются интерпретацией модели и явно отделены от проверенных фактов.
